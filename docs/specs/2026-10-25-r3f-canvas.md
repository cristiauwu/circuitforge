# Spec: Lienzo R3F con arrastrar y soltar (etapa UI-2)

**Fecha:** 2026-10-25
**Estado:** propuesta para aprobación
**Prerrequisitos:** `docs/design/DESIGN.md` v2.1, `docs/design/2026-10-25-shell-navegable.md`, `docs/specs/2026-10-25-circuitforge-especificacion.md`
**Alcance:** el lienzo real del editor. **Sin** solver ni simulación.

---

## 1. Objective

Sustituir el lienzo SVG de ejemplo por un **lienzo Three.js real** (React Three Fiber) donde se puedan **colocar, mover, rotar y eliminar componentes**, y **cablear sus pines**. Es el corazón del OE-1.

**Por qué ahora.** El stack fija desde el inicio que el lienzo va sobre Three.js en cámara ortográfica (decisión **D-3**), precisamente para no reescribirlo cuando llegue el 3D. El lienzo actual es una maqueta SVG con posiciones escritas a mano: sirve para ver la pantalla, no para trabajar en ella.

**Usuario:** un estudiante que arma un circuito en el navegador.

**Éxito:** un usuario nuevo construye «fuente + resistencia + LED» cableado **en menos de 5 minutos sin ayuda** (criterio de aceptación textual del OE-1).

|---|---|---|---|
| Render 3D | `three` | **0.186.1** | R3F exige `>=0.156` ✓ |

## 3. Decisión clave: qué se renderiza en 3D y qué no

Esta es la decisión de diseño de la etapa, y determina todo lo demás.

**El lienzo es un `<Canvas>` de R3F con cámara ortográfica. Pero los símbolos de componente se dibujan como texturas/texto, no como geometría 3D.**

Razón: un símbolo esquemático es **plano por definición**. Modelarlo como malla 3D es trabajo de fase 2 (cuando existan los GLB). Lo que R3F aporta **hoy** es:

1. **Una cámara con zoom y paneo reales** — el lienzo deja de ser una imagen estática.
2. **Coordenadas de mundo** para cada componente, con la rejilla como referencia espacial.
3. **Hit-testing correcto**: seleccionar y arrastrar con precisión, incluso con zoom.
4. **La base para el 3D** sin reescribir (D-3).

**Cómo se dibujan los símbolos:** con `drei`'s `<Html>` anclado a cada objeto, o con `<Svg>` de drei. Se elige `<Html>` porque reutiliza los componentes SVG que ya existen (`SchematicSymbol.tsx`), sin duplicar 22 dibujos en geometría.

> **Riesgo y mitigación:** `<Html>` crea nodos DOM superpuestos al canvas. Con 60 componentes sería costoso. **Medido y decidido en la tarea 4**: si el rendimiento baja de 60 fps con 30 componentes, se cambia a `<Svg>` de drei (que dibuja en la escena) sin tocar el resto. Se mide, no se supone.

## 5. Project Structure

```
apps/web/src/
├─ features/editor/
│  ├─ canvas/
│  │  ├─ CircuitCanvas.tsx      # <Canvas> + cámara ortográfica + rejilla
│  │  ├─ SceneComponent.tsx     # un componente de la escena (arrastrable)
│  │  ├─ SceneWire.tsx          # un cable entre dos pines
│  │  ├─ useGridSnap.ts         # conversión pantalla→mundo + imán a rejilla
│  │  └─ useDragComponent.ts    # lógica de arrastre (pointer events)
│  ├─ Palette.tsx               # (existe) origen del arrastre
│  └─ Inspector.tsx             # (existe) refleja el componente seleccionado
└─ lib/
   └─ editor/
      ├─ useEditorStore.ts      # estado del editor: proyecto, selección, historial
      └─ history.ts             # pila de undo/redo
```

**Por qué `zustand` entra ahora y no antes:** hasta hoy el estado de UI cabía en `useState`. Con netlist, selección, historial y arrastre en curso, el estado es de dominio y compartido entre paleta, lienzo e inspector. El stack ya lo fijaba (P-5, ADR del spec).

## 6. Code Style

```tsx
/**
 * Un componente colocado en la escena.
 *
 * El `netlist` es la fuente de verdad (D-1): este componente NO guarda su
 * posicion, la LEE del proyecto. Arrastrar actualiza el proyecto, y el render
 * es consecuencia.
 */
function SceneComponent({ componentId }: { componentId: string }) {
  const component = useEditorStore((s) => s.project.components.find((c) => c.id === componentId))
  const move = useEditorStore((s) => s.moveComponent)
  const { bind } = useDragComponent(componentId, move)

  if (!component) return null
  return (
    <group position={[component.position.x, component.position.y, 0]} {...bind}>
      <SchematicSprite typeId={component.typeId} />
    </group>
  )
}
```

Convenciones (heredadas del proyecto):
- Identificadores en inglés, texto de UI en **español** (RNF-10).
- `Project`/`Component` vienen de `@circuitforge/netlist`. **No se duplican tipos.**
- Ningún literal de color: tokens de `DESIGN.md`.
- Radios, duraciones y curvas: los tokens del sistema.

## 7. Testing Strategy

| Nivel | Herramienta | Qué cubre |
|---|---|---|
| Unidad | **Vitest** | `useGridSnap` (pantalla→mundo, imán), `history` (undo/redo), acciones del store |
| Integración | **Vitest** | El store con `connectPins`: colocar → cablear → undo |
| Navegador | **CDP** (`.tools/`) | El lienzo monta, se puede arrastrar, la consola está limpia, los fps se mantienen |

**Lo que NO se testea con unitarios:** el render de Three.js. Un `<Canvas>` necesita WebGL real; se verifica en navegador con capturas y medición de fps.

**Cobertura mínima:** las funciones puras (`useGridSnap`, `history`) al 100 %. El store, con los caminos de error incluidos (arrastrar a coordenadas inválidas, undo en pila vacía).

## 8. Boundaries

**Always**
- Correr `.tools\verify.cmd` antes de cada commit.
- Leer la posición del proyecto, nunca duplicarla en el componente.
- Mantener el presupuesto de glass en 3 superficies.
- Verificar en navegador real, no solo leyendo código.

**Ask first**
- Cambiar de `<Html>` a `<Svg>` de drei (afecta a cómo se dibujan los 22 símbolos).
- Añadir cualquier dependencia fuera de las 4 de la sección 2.
- Tocar `packages/netlist` (es contrato del dominio y ya está probado).

**Never**
- Introducir `three` en `packages/*` (rompería P-1: dominio puro, sin DOM).
- Animar `width`/`height`/`top`/`left` (V-3).
- Añadir `box-shadow` de elevación (V-2).
- Escribir literales de color, radio o duración.

## 9. Success Criteria

Verificables, no aspiracionales:

| # | Criterio | Cómo se comprueba |
|---|---|---|
| 1 | El lienzo monta un `<Canvas>` de R3F con cámara ortográfica | Inspección del DOM: existe `<canvas>` y `element.style` con WebGL |
| 2 | Se ve la cuadrícula y los 4 componentes de ejemplo | Captura + medición de objetos en la escena |
| 3 | **Arrastrar** un componente lo mueve y la posición queda imantada a la rejilla | Test unitario de `useGridSnap` + verificación manual en navegador |
| 4 | **Seleccionar** un componente puebla el inspector | El inspector muestra su nombre, parámetros y pines |
| 5 | **Rotar** en múltiplos de 90° (0/90/180/270, nunca otro valor) | Test unitario + el inspector refleja el ángulo |
| 6 | **Eliminar** con `Supr` y **deshacer** con `Ctrl+Z` | Test del store con historial |
| 7 | **Cablear** dos pines crea un net (reutiliza `connectPins`) | Test de integración sobre el store |
| 8 | La validación **bloquea** un cortocircuito power→gnd (V-1) | Test: `canConnect` devuelve `allowed: false` y el lienzo no crea el net |
| 9 | **Zoom y paneo** funcionan sin romper la selección | Verificación manual + medición de coordenadas |
| 10 | Consola limpia | CDP: 0 errores, 0 warnings |
| 11 | **≥55 fps** con los componentes en pantalla | Medición de `requestAnimationFrame` en el navegador |
| 12 | Sin desbordamiento a 320/768/1024/1440 px | Verificación de responsive |
| 13 | El bundle no supera **200 KB gzip** inicial | Salida de `vite build` |

**El criterio 11 es el que decide la arquitectura de la sección 3.** Si `<Html>` no lo alcanza, se cambia a `<Svg>`.

## 10. Open Questions

1. **¿El arrastre debe funcionar también en táctil?** Asumo que sí (pointer events cubren ambos), pero no lo he verificado en un dispositivo real.
2. **¿Los cables se dibujan como curvas Bézier o como segmentos ortogonales?** Asumo Bézier (como el lienzo actual); un editor EDA profesional suele preferir ortogonal.
3. **¿Cuántos niveles de undo?** Asumo 50, suficiente para una sesión de trabajo sin consumo apreciable.

Ninguna bloquea el arranque: son decisiones con valor por defecto razonable, y las tres son reversibles sin rehacer la etapa.
